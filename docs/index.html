1 — Memory
CLAUDE.md + rules/ — the always-on brain
Loaded at every session. Tells Claude who you are, what your project does, and what rules to follow — so you never repeat yourself.
📄 CLAUDE.md — root project memory
# Acme Corp — Salesforce Org (Production) Org alias: acme-prod API version: 61.0 SFDX root: force-app/main/default/ ## Non-negotiable rules - Never put SOQL or DML inside for-loops - Always use USER_MODE in SOQL queries - Minimum 85% test coverage on all Apex - Deploy cmd: sf project deploy start ## Folder conventions - Apex classes → classes/ - Flows → flows/ - LWC → lwc/ - Triggers → triggers/
📂 rules/apex.md — path-scoped (*.cls only)
--- paths: ["force-app/**/*.cls"] --- ## Apex-specific (loads only for .cls files) - Bulkify: handle 200+ records always - Use TestDataFactory in @isTest classes - Wrap all DML in try/catch blocks - @AuraEnabled(cacheable=true) only for read-only methods - Naming: ClassNameService.cls, not Util - No hardcoded Org IDs or Record Types - Use Custom Metadata, not Custom Settings
⚡ Rules only activate when Claude opens a matching file — keeps CLAUDE.md under 200 lines

3 — Commands
Slash commands — you call, Claude executes
Single .md files in .claude/commands/. Filename = slash command. You trigger them manually. Use $ARGUMENTS to pass parameters at call time.
📄 .claude/commands/deploy.md → /deploy
Deploy current changes to a Salesforce org. Target org: $ARGUMENTS (default: acme-prod) 1. Generate manifest: sf project generate manifest \ --output-dir manifest \ --from-org $ARGUMENTS 2. Deploy: sf project deploy start \ --manifest manifest/package.xml \ --target-org $ARGUMENTS 3. Verify deployment status 4. List deployed components 5. If failure: show error + suggest fix
📄 .claude/commands/run-tests.md → /run-tests
Run Apex tests for the $ARGUMENTS class. sf apex run test \ --class-names "$ARGUMENTS" \ --code-coverage \ --result-format human \ --target-org acme-prod Report: - Overall coverage % - Per-method coverage - Failed tests with stack trace - Suggest fixes if tests fail
📄 .claude/commands/soql.md → /soql
Run a SOQL query: $ARGUMENTS sf data query \ --query "$ARGUMENTS" \ --target-org acme-prod - Format results as a table - Flag missing indexes - Warn if query returns > 10k rows - Suggest optimizations
📄 .claude/commands/retrieve.md → /retrieve
Retrieve $ARGUMENTS metadata from org. sf project retrieve start \ --metadata "$ARGUMENTS" \ --target-org acme-prod \ --output-dir force-app/ After retrieval: - List files changed - Show git diff summary - Flag any schema changes

4 — Skills
Auto-triggered expertise packages
Skills are FOLDERS with a SKILL.md inside. Unlike commands (you call), Claude automatically detects when a skill is relevant and loads it. Skills can also bundle scripts and reference docs.
📂 skills/apex-best-practices/SKILL.md
--- name: apex-best-practices description: Apply when writing or reviewing any Apex code for Salesforce --- ## Bulkification - Always handle 200+ records in triggers - Use List/Map collections, never loop SOQL - One SOQL query before the loop, not inside ## Security (CRUD/FLS) - USER_MODE on ALL SOQL queries - Use bind variables — no string concat ## Tests - TestDataFactory for all test data - @isTest(SeeAllData=false) always - Assert on specific field values
📂 skills/soql-optimizer/SKILL.md
--- name: soql-optimizer description: Apply when writing SOQL queries or reviewing data access patterns --- ## Query best practices - Filter on indexed fields first (Id, Name, ExternalId__c, lookups) - Specify only needed fields — no SELECT * - LIMIT on large objects (Account, Contact) - Use relationship queries over multiple single-object queries ## Anti-patterns to catch - SOQL inside Apex for-loops → BLOCK - Missing WHERE on large objects - Non-selective queries on 100k+ records
💡
Commands vs Skills — the key difference
Commands = you explicitly type /command-name to run them.
Skills = Claude reads the task context, recognizes a match to the skill's description, and loads it automatically — you never have to invoke it.
5 — Agents
Specialist subagents — isolated context windows
Markdown files in .claude/agents/ with YAML frontmatter. Claude spawns them in a separate isolated context when the task matches. They do heavy work without polluting your main session.
📄 agents/apex-reviewer.md
--- name: apex-reviewer description: Expert Apex code reviewer. Invoke when reviewing trigger handlers, service classes, or before PR merges. model: sonnet tools: Read, Grep, Glob --- You are a senior Salesforce developer reviewing Apex code. Check for: 1. SOQL/DML inside for-loops 2. Missing CRUD/FLS enforcement 3. Governor limit risks (heap, CPU) 4. Test coverage gaps 5. Naming convention violations Return: severity-rated report (High / Medium / Low per issue)
📄 agents/test-generator.md
--- name: test-generator description: Generates Apex test classes. Invoke when asked to write tests for a new Apex class or trigger. model: sonnet tools: Read, Write, Bash --- 1. Read the target Apex class fully 2. Identify all methods + branches 3. Write @isTest class with TestDataFactory 4. Target 90%+ code coverage 5. Deploy with: sf apex run test --class-names X 6. Report: coverage % + any failures

🔒 Isolated Context

Agent work happens in its own context window. Thousands of tokens of intermediate exploration never reach your main session.

🎯 Tool Restrictions

apex-reviewer only has Read/Grep/Glob — it cannot write files. test-generator gets Write. Minimal footprint by design.

🤝 Report Back

Agent completes its task, compresses findings, and returns a clean summary to your main session. No context bloat.

6 — Hooks
Deterministic event automation — the enforcer layer
Hooks fire at specific lifecycle events and run shell scripts, prompts, or HTTP calls. Unlike skills or CLAUDE.md, hooks are deterministic — the model cannot skip them. Exit code 2 blocks any action, always.
⚡
CLAUDE.md rules are advisory. Hooks are enforced. A CLAUDE.md rule saying "never deploy to production without tests" can be forgotten. A PreToolUse hook that exits 2 when it detects that pattern will block it every single time, even in --dangerously-skip-permissions mode.
All hook event types
PreToolUse
Fires BEFORE a tool runs. Can inspect and block. Most powerful event.
⛔ CAN BLOCK
PostToolUse
Fires AFTER tool completes. Perfect for auto-formatting, running tests, logging.
✅ REACTIVE
PostToolUseFailure
Fires when a tool fails. Inject context to help Claude diagnose and retry.
⚠️ ON ERROR
UserPromptSubmit
Fires when you submit a prompt, before Claude processes it. Enrich or validate input.
📝 PRE-PROMPT
Stop
Fires when the main agent finishes. QA checks, final validation, notifications.
🏁 ON FINISH
SubagentStop
Fires when a subagent completes. Cleanup or validation after agent tasks.
🤖 SUBAGENT
Notification
Fires when Claude needs attention. Route alerts to Slack, email, or desktop.
🔔 ALERT
PermissionRequest
Fires at permission dialogs. Auto-approve safe patterns, deny risky ones.
🔐 GATING
SessionEnd
Fires on session termination. Generate summaries, persist state, cleanup.
🌙 TEARDOWN
⚙️ settings.json — Salesforce hooks configuration
{ "hooks": { // BLOCK: Never deploy to production without tests "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "python3 .claude/hooks/block-prod-without-tests.py" }] }], // REACT: Auto-run Apex tests after any .cls edit "PostToolUse": [{ "matcher": "Write|Edit", "hooks": [{ "type": "command", "command": "bash .claude/hooks/auto-run-apex-tests.sh" }] }], // VALIDATE: Prompt-based QA check before Claude stops "Stop": [{ "hooks": [{ "type": "prompt", "prompt": "Check: deployment verified, tests passing, coverage met?" }] }], // NOTIFY: Slack alert when Claude needs input "Notification": [{ "hooks": [{ "type": "command", "command": "curl -s -X POST $SLACK_WEBHOOK -d '{\"text\":\"Claude needs input\"}}'" }] }] } }
🐍 block-prod-without-tests.py (PreToolUse)
import json, sys data = json.load(sys.stdin) cmd = data.get("tool_input",{}).get("command","") # Block deploy to prod without running tests if "acme-prod" in cmd and "--no-tests" in cmd: sys.stderr.write( "BLOCKED: Cannot deploy to production " "without running tests first.\n" "Remove --no-tests flag.") sys.exit(2) # 2 = block the action sys.exit(0) # 0 = allow
🔢 Exit code semantics
Exit 2 → BLOCK
Stops the tool from executing. Claude sees stderr as an error message and adjusts its plan.
Exit 0 → ALLOW
Hook succeeded. Tool execution proceeds normally.
Exit 1 → WARNING
Non-blocking error. Action still proceeds. Warning shown to user only.
7 — MCP Servers
Connect Claude to your live Salesforce org and beyond
MCP (Model Context Protocol) gives Claude real-time access to external systems — your Salesforce org, GitHub, JIRA, databases, web search. Configured in .mcp.json at project root (committed to git).
📄 .mcp.json (project root — committed to git)
{ "mcpServers": { "salesforce": { "type": "stdio", "command": "npx", "args": ["-y", "@salesforce/mcp-server"], "env": { "SF_ORG_ALIAS": "acme-prod", "SF_ACCESS_TOKEN": "${SF_ACCESS_TOKEN}" } }, "github": { "type": "http", "url": "https://api.github.com/mcp/", "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" } }, "jira": { "type": "stdio", "command": "npx", "args": ["-y", "@atlassian/jira-mcp"], "env": { "JIRA_API_TOKEN": "${JIRA_TOKEN}" } } } }

🏢 Salesforce MCP

Claude gets tools: sf_query_records, sf_deploy_metadata, sf_run_tests, sf_get_object_fields — direct access to your live org data and schema.

🎫 JIRA MCP

Claude reads the JIRA ticket, implements the feature, updates ticket status, creates PR, and links it back — the full workflow from a single prompt: "build ticket SF-123".

🐙 GitHub MCP

Create branches, open PRs, read issues, trigger CI/CD — all from Claude's context, grounded in your Salesforce code changes.

8 — settings.json
The permission and policy layer
Controls exactly what Claude can and cannot do. Deny rules always win. Committed to git for team-wide enforcement. settings.local.json holds personal overrides (gitignored).
⚙️ .claude/settings.json
{ "$schema": "https://json.schemastore.org/...", "model": "claude-sonnet-4-6", "permissions": { "allow": [ "Bash(sf project deploy start *)", "Bash(sf apex run test *)", "Bash(sf data query *)", "Bash(git add * && git commit *)", "Read(force-app/**)", "Write(force-app/**)" ], "deny": [ "Bash(sf org delete *)", "Bash(rm -rf *)", "Read(.env)", "Read(./secrets/**)" ] }, "env": { "SF_ORG_ALIAS": "acme-prod" } }
⛔ Deny (always wins)
If a command matches a deny rule, it's blocked — regardless of any allow rule at any scope level. Deny is absolute.
✅ Allow (pre-approved)
Matching commands run without a permission prompt. Build this list gradually by accepting recurring prompts.
❓ Ask (middle ground)
Anything not in allow or deny → Claude asks before proceeding. Safe default for new commands.
Pro tip: start with a minimal settings.json and let Claude prompt you. Add to allow list as you identify safe recurring commands.
9 — Plugins
Packaged bundles — install once, share team-wide
A plugin packages commands, agents, skills, hooks, and MCP servers into one installable unit. Install with claude plugin install. Use --scope project to share via git.
💻 Installing a Salesforce DX plugin
# Install for entire team (shared via git) claude plugin install salesforce-dx@marketplace \ --scope project # What it adds automatically: commands/ → /sf-deploy, /sf-retrieve, /sf-test, /sf-describe-org agents/ → metadata-analyzer, test-coverage-reporter skills/ → apex-patterns/, lwc-standards/, soql-optimizer/ hooks/ → block-dml-loops.sh, enforce-85pct-coverage.py

👥 Team Scope

--scope project writes to .claude/settings.json and is committed to git. Every developer who clones the repo instantly gets all commands, agents, skills, and hooks.

👤 Personal Scope

--scope local writes to gitignored settings.local.json. Personal plugins stay on your machine and don't affect teammates.

🌐 Global Scope

--scope user (default) writes to ~/.claude/settings.json. Available across all your projects without committing anything.

Real-World Scenarios
End-to-end Salesforce automation examples
Scenario 1 — Full Feature Deployment

You: "Build JIRA ticket SF-247 and deploy to sandbox"

1
MCP (JIRA) reads ticket SF-247 — feature: add Lead scoring field, validation rule, and flow
2
Skill (apex-best-practices) auto-loads because Claude will write Apex validation
3
Tools (Write) creates LeadScoringService.cls, LeadScoringTrigger.cls, and Flow XML
4
Hook (PostToolUse) auto-triggers after Write → runs sf apex run test automatically
5
Agent (test-generator) is spawned to write LeadScoringServiceTest.cls (90%+ coverage)
6
Command /deploy runs sf project deploy start → deploys to sandbox org
7
Hook (PreToolUse) validates deploy command — allows sandbox, would block prod if --no-tests
8
MCP (JIRA + GitHub) updates ticket to "In Review", opens PR with deployment confirmation
Scenario 2 — Code Review + Quality Gate

You: "Review OpportunityTrigger.cls before merging"

1
Agent (apex-reviewer) spawned in isolated context — reads trigger with Read/Grep/Glob only
2
Skill (apex-best-practices) loaded into agent context — provides review criteria
3
Agent finds: SOQL in loop on line 47 (High), missing CRUD check on line 92 (High)
4
Hook (Stop + prompt-type) validates: "Did Claude produce a severity-rated report with fixes?" — if No, forces continuation
5
Tools (Edit) applies fixes with refactored bulkified queries and added FLS checks
6
Hook (Notification) sends Slack message: "OpportunityTrigger review complete — 2 issues fixed, ready to merge"
Scenario 3 — Overnight Automated Org Audit

You: "Audit the full org for governor limit risks tonight"

1
Tools (Glob) discovers all 200 Apex trigger files in force-app/main/default/triggers/
2
Agent (apex-reviewer) spawned repeatedly in isolated forks — reviews each trigger batch independently
3
Hook (SubagentStop) fires after each batch — logs findings to audit_report.md, keeps running tally
4
MCP (Salesforce) queries org for actual execution stats to validate findings against real-world data
5
Hook (Stop) fires at completion — generates full PDF-ready audit report, sends email via Notification hook
